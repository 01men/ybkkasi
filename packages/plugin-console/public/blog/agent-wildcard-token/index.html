Agent 拿着一把万能 token 横冲直撞：一次真实的越权复盘

那天我们在自己的代码里发现了一个鉴权漏洞。它不是设计缺陷，是一个 40 行函数里漏传的两个字段。

这篇文章讲三件事：这个漏洞怎么被发现的、它为什么是「万能 token」问题的典型形态、以及我们把鉴权从「一把钥匙」改成「一串钥匙」时踩过的坑。

不含产品宣传，只含代码和教训。

一、漏洞长什么样

元冰可把自己的平台同时暴露成三种入口：

  • REST 网关（/api/*），给控制台和外部系统调
  • MCP Server 端点（/mcp，JSON-RPC over HTTP），给 Claude Code、dsh 这类 MCP 客户端连
  • dsh 宿主桥，给 DeepSeek Harness 里的插件调

三条入口，理论上应该共用同一套鉴权中间件、同一套权限点、同一个主体结构。这是设计前提。

我们的 MCP 端点鉴权代码在 packages/plugin-console/src/routes/bridge.ts，函数叫 mcpCallerFromToken。它做的事情看起来很标准：读 Authorization 头，验 Bearer 令牌，构造一个 CallerInfo 返回。

某天有人（就是我）读这段代码的时候发现，构造 CallerInfo 时是这样的：

return {
  kind: verified.principal.type,
  principalId: verified.principal.id,
  ...(verified.principal.type === 'human' && verified.principal.refId
    ? { userId: verified.principal.refId }
    : {}),
  name: verified.principal.name,
  permissions: verified.scopes,
  actChain: verified.actChain,
}

问题在于：当 principal.type === 'machine'（也就是 Agent 用的机器令牌）时，refType 和 refId 两个字段没有被带上去。

refType/refId 是什么？它标识「这个凭证背后关联的是哪个具体资源」。human 凭证背后是一个用户，machine 凭证背后是一个 Agent。

这两个字段一旦丢了，后续所有「按资源反查任务归属」的逻辑就全部失灵。

二、它是怎么变成越权的

单独丢两个字段，看起来只是个「数据不完整」。它变成越权，是因为下游有一段这样的逻辑。

plugin-exec-hub 里有个工具叫 exec_claim，Agent 在执行任务前要调它取执行锁。它需要知道「这次执行属于谁」。判断依据是：

exec.principal.refType === 'agent' && exec.principal.refId === 当前Agent

REST 链路上的鉴权中间件是从完整的主体记录里构造 CallerInfo 的，refType/refId 一直在。所以同一个 Agent，走 REST 调 exec_claim，归属判断正确；走 MCP 调 exec_claim，refType 是 undefined，判断条件永远不成立。

代码里给它留了退路：

// 非受管（resolveByCaller=null）→ 落回旧 exec_claim 语义（保持兼容）

于是所有从 MCP 进来的执行，主体都被判定为「非受管」，走旧的宽松语义。

翻译成人话：MCP 通道上，Agent 的执行任务不属于任何 Agent。

后果是连锁的：

  1. 执行锁拿不到归属，做不了「一个 Agent 不能抢另一个 Agent 的活」这类约束
  2. 审计日志记下来的主体不完整，事后追责追不到具体 Agent
  3. 成本归因算不出来——这条消耗记不到任何 Agent 头上，最后落进「无法归类」桶里
  4. 权限点虽然还在令牌上（permissions: verified.scopes 照常带了），但缺少资源维度的约束，等于一把万能钥匙开所有门——只要这个钥匙能进门

最后一条是关键。多数人理解越权时想的是「令牌权限太大」，但这次的真实情况是「令牌权限刚好够，主体身份丢了」。 权限检查全过，只是没人能说清「过的人是谁」。

三、为什么它躲过了两轮测试

三个原因叠在一起，缺一不可。

第一，两条链路的 CallerInfo 结构本来就不一致。 REST 走中间件构造，带全字段；MCP 走独立函数构造，只带部分字段。这两个函数在代码里相隔几百行，没有共享类型约束——CallerInfo 的 refType/refId 是可选字段（refType?: string），TypeScript 不会报错。

第二，测试只测了「能调通」。 早期的 MCP 端点测试断言的是：正确的令牌能返回工具列表、无令牌返回 401、过期令牌返回 401。这些都是入口测试。没有任何一条断言去检查「Agent A 的令牌执行的任务，归属是不是 Agent A」。

第三，兼容性退路掩盖了它。 resolveByCaller=null → 落回旧语义 这行是当年为了平滑迁移留的。它让系统在任何新链路出问题时都不会崩，代价是故障静默降级成了宽松模式。这类「为了不炸而写的兜底」是治理平台里最危险的代码形态，因为它把「明确的失败」换成了「看不见的失守」。

四、我们怎么改的

改动本身只有几行。bridge.ts 里补上 machine 分支：

...(verified.principal.type === 'machine'
  ? { refType: verified.principal.refType, refId: verified.principal.refId }
  : {}),

补完之后 /mcp 和 /api/tools/execute 两条链路的 CallerInfo 结构完全一致：machine 主体带 refType/refId，human 主体带 userId。

但真正花时间的是后面的三件事。

把两条链路的主体结构对齐这件事写成了断言。 不是加日志，是加测试断言：任何构造 CallerInfo 的代码路径，都必须覆盖齐这四个字段（human: userId；machine: refType/refId），少一个直接让测试变红。我们现在有 1822 条自测断言，这条归属一致性检查在里面。

删掉了那条兼容性退路。 主体解析不出来就是解析不出来，返回明确错误让调用方知道。理由很直接：治理平台宁可拒绝一次合法请求，也不能放过一次归属不明的执行。

把「主体不完整」变成一类可观测事件。 主体字段缺失时写一条审计日志，带上来源入口（rest / mcp / dsh）。这次故障真正被发现的路径不是测试，是有人注意到 MCP 链路的成本里「无法归类」那一栏异常高。

五、从这一个 bug 想到的更大的事

修完这个漏洞，我们把「万能 token」这个词重新想了一遍。

问题从来不是「要不要发令牌」，而是令牌代表什么。

传统 RBAC 的模型是一个主体对应一个角色，角色对应一组权限。这在人有明确岗位的时候成立。Agent 不一样——同一个 Agent 在不同时刻需要不同的权限：

  • 白天做数据分析，只需要读数据库
  • 晚上做归档，需要写存储
  • 被另一个 Agent 委托时，需要临时多一层权限

我们的解法是把令牌拆成四层：

层字段作用
主体principal.type + refId这是谁
委托actChain谁让它干的（on-behalf-of 链，签发时叠加）
权限scopes能做什么（94 个权限点，最小声明）
归属refType + refId消耗记到哪个资产头上

关键在第四层。前三层决定「允不允许」，第四层决定「算谁的」。 没有第四层，一个 Agent 能做的事和另一个 Agent 能做的事可能完全一样，但所有消耗和审计都是匿名的——这就是万能 token 的真正形态。

委托链也是同理。人给应用发令牌，应用再给 Agent 发令牌，这条链如果不记下来，审计时就只能看到最外层的应用，看不到实际是谁在操作。actChain 是把这条链钉进令牌里的，审计侧可以完整还原。

六、几条我们自己的规矩

写下来给同样在做 Agent 治理的团队参考。

一条链路一个 CallerInfo 构造函数。 别在每个入口各写一份主体解析。我们的 /mcp 最初独立写了解析函数，现在虽然还是两处代码，但有断言强制它们结构一致。更好的做法是抽成一个函数，让类型系统帮你记住。

治理平台的兜底逻辑默认应该是 fail-closed。 「解析不出来就退回旧语义」这种写法在任何 CRUD 系统里都是罪，在治理系统里是更大罪。它把「告警会响」换成了「日志里多个桶」。

测试要测归属，不要只测鉴权。 「无令牌返回 401」测的是入口。「A 的令牌产生的副作用归属 A」测的是治理。这两件事是完全不同的断言，我们早期只写了前者。

主体字段缺失是可观测事件，不是静默降级。 我们的 /mcp 端点按设计就要求 Bearer 令牌，匿名 introspection 请求会直接 401。这看起来很不友好（有些第三方 MCP 目录要求匿名可探测），但放宽鉴权去迎合检查是不可接受的——那正好是「万能 token」问题本身。

边界

我们解决的「万能 token」问题是：Agent 拿到的令牌权限过大、缺少资源归属、委托链丢失、审计追不到人。

我们没解决的：

  • 令牌泄露后的止损（吊销广播链路有了，但不做 token 指纹检测）
  • Agent 决策过程的合规（我们只管调用，不管推理）
  • 跨组织边界的权限联邦（OIDC Provider 接了，但不做跨租户授权协商）

这些都是别的层的问题。我们把「谁能调什么、消耗算谁的、出事查得到谁」这三件事收在了一个模型里，剩下的没做。
