企业 AI 资产成熟度自测：你的团队在第几级？

先问三个问题，不用查资料，凭印象答：

  1. 公司现在有几个 MCP 服务在跑？（不是「大概」，是准确数字）
  2. 上个月 AI 花了多少钱？拆到部门，排前三的是谁？（不是总额）
  3. 昨天有人调了一次客户数据接口，是谁调的？

三个都能立刻答上来，你的团队在 L3 以上。三个都答不上，在 L0。

只有一个能答上来，是最常见的状态——也是最危险的状态。 因为那一个通常让人误以为「我们在管 AI」。

下面五级，每级给出可验证的判据。不用自评，直接跑命令对。

一、五级的判据

级别一句话可验证判据
L0 散装东西在跑，没人有名单问「有几个」，三个部门给三个数
L1 有清单有一张表，但是人填的表里超过一周没更新；有人离职后条目还在
L2 有台账从系统里自动出，不是人填的有一个接口，能返回全部资产的当前状态
L3 有归口每个资产有归属人、每次调用有归属任一次调用能回答「谁、为什么、花了多少」
L4 有制度权限和成本在调用发生时强制生效归口字段缺失时，调用直接失败而不是记一笔

这五级不是能力等级，是「能回答哪些问题」的等级。L2 能回答「有什么」，L3 才能回答「谁在用」，L4 才能回答「该不该让他用」。

大部分团队的卡点在 L1→L2，而绝大部分精力花在 L0→L1。

二、L0 到 L1：清单的错觉

L0 的特征不是「没有管理」，是三份互不相交的名单。

我们内部真实经历：IT 说「MCP 服务七八个」，业务说「Agent 十几个，具体哪些还在用不知道」，财务说「模型开了四家账号，月账单四万多」。三份台账，零重合。

于是建了一张 Excel。这就是 L1。

L1 的问题从来不是「没建」，是建完之后它就不再是真的。三个具体腐烂方式：

  • 人一离职，条目变孤儿。 表里还写着「负责人：张三」，张三三个月前走了。
  • 新东西永远滞后入表。 有人周五接了个 MCP 服务自己试，下周一才想起来没登记——如果他没想起来，就永远不在表里。
  • 状态列是愿望不是事实。 表里写「运行中」，实际早就挂了，因为没人去改。

判据很简单：这张表如果今天停止人工维护，多久之后它会开始说谎？ 答案是「一周内」的话，你还在 L1，不管表做得多漂亮。

我们的判断是：L1 不该作为目标级，它只是必经的过渡态。 在 L1 上做的所有优化（加字段、加颜色、加自动提醒）都是给一个必然腐烂的东西续命。

三、L2 到 L3：台账的价值在问句，不在报表

L2 的定义是有接口，不是有页面。区别在于：页面是给人看的，接口是能被查的。

我们的 /api/assets/inventory 返回一个扁平数组，六类资产混在同一个 items 里，每条只有 11 个字段：type / id / slug / name / status / health / org / updatedAt / calls / costCents。

只有 11 个。版本号、endpoint、鉴权方式、依赖拓扑这些类内属性，一律不进统一模型。

因为台账的价值全在「能被问」，而不在「记得全」。 统一之前你问不出这些问题，因为答案散在六个接口里、字段名都不一样：

  • 「AI 平台部现在挂了几个在线的东西？」→ 按 org + 在服状态，一行查询
  • 「最贵的三项是什么？」→ 按 costCents 降序
  • 「哪些资产 30 天一次没被调用过？」→ calls === 0

第三条是我们内部最有用的查询，也是最容易给出错误答案的一条。

四、L3 的门槛：每个 0 必须是真的 0

这一节是整篇文章的重点，也是我们踩得最深的一脚。

实测 27 个资产里 calls === 0 的有 20 条。看起来是个大发现——74% 的 AI 资产没人用。但拆开看：

类型零调用这个 0 是真的吗
mcp1（灰度中）真
skill2（安装数 0）真
model2（待接入）真
nas2（草稿态）真
app0—
agent6（全部）假 0

六个 Agent 的 calls 恒为 0，原因不是没人用，是这条链路上取用量时传的是 undefined，落进默认分支写了 0。查询逻辑没查错，数据从源头就是假的。

后果不是「那一格不好看」，是依赖这一格的每一个问句都变成半真的：

  • 「找出闲置资产」→ 六个在用的 Agent 混进清单
  • 「闲置率 74%」→ 真实值可能是 52%，也可能是 20%
  • 有人拿着这份报表去砍预算 → 砍掉的是正在用的东西

我们当时的临时做法是在查询里先 WHERE type != 'agent'。这是个技术债，但它比「假装 0 是真的」诚实。

L3 的真实门槛不是「有归属字段」，是「每个 0 都经过确认」。 一条记录说「这个月没人用」，你得能回答「你怎么知道没人用，而不是你没记」。

同理，成本字段：六类里有三类是硬编码 0。所以对外我们从不引用「总成本」以外的任何拆分——因为拆分里有三类的分母是假的。

五、L4：让归口字段能弄失败调用

L3 和 L4 的差是一行代码的位置。

L3 的做法常见于「事后补录」：调用发生，日志记一笔，后台任务异步补上部门字段，补不上就留空。

L4 的做法是在消耗发生的那一刻强制写上，并且允许它让调用失败。

这两者的差别在概率上极大：

  • 事后补录的补齐率，取决于上游字段质量。我们的实测是补不上的那些永远不会被补上，而且没人会发现——因为空值不报警。
  • 强制写入的失败率，会在第一天就暴露成 500 错误。难看，但你知道。

一个字段如果可以在缺失的情况下让流程继续，它就一定会缺失。 这不是纪律问题，是任何有并发和重试的系统里的必然。

代价是真实的：上线第一周会有调用被拒。这是必须付的价，因为账单月底出来的时候，「某个部门这个月花了多少」这个问题只有一个正确答案，没有「大概」。

六、你的自测：跑这四条

不用看我们的产品，跑这四行就够判断自己在哪一级：

# L2 判据：有没有一个接口能返回全部资产的当前状态
curl -s <你的平台>/api/assets/inventory | head -c 200
# 返回的是接口数据 → L2 起步；返回 HTML → 还在 L1

# L3 判据：任取一条资产，问它的归属和用量
# 能否一句话回答「谁负责、上月调用几次、花多少」

# L3 判据（关键）：随机挑 5 个「30 天零调用」的资产，人工确认
# 5 个里有 1 个其实在用 → 你的 0 是假的，回 L2

# L4 判据：把某个资产的归属部门清空，然后调用它
# 调用成功并记了一笔空归属 → L3
# 调用被拒绝，报错说缺归属 → L4

最后一条是最硬的判据，也是最容易被跳过的一条——因为它真的会让一次调用失败。

七、我们现在在哪一级

诚实地说：L3，正在补 L4 的洞。

具体的缺口，列清楚：

  • calls / costCents 六类里有三类是硬编码 0 → 拆分口径不完整，对外只引总数
  • Agent 的用量取用走的是空参数默认分支 → 「零调用」查询需要排除 agent 才可信
  • 归口字段在部分通道是事后补，不是强制写 → 还没到「缺了就失败」
  • collections 这个数在 72 到 86 之间反复（装配态差异），所以对外文案里任何地方都不引用它——一个会涨也会跌的指标，是装配态的伪指标，不是业务指标

这四条都是我们自己写在文档里的，不是别人挖出来的。 因为一个台账如果不标出自己漏了什么，它就没有价值——一份每格都填满的台账，通常有三分之一的格子是拍的。

L4 不是终点。但 L3 到 L4 这一步，是所有「AI 花了多少钱」的问题从「说不清」变成「说得清」的唯一一步。
