98 个 MCP 工具，四个 MCP 目录里一个都搜不到

上个月有个用户在群里问：「你们的 MCP Server 在 Glama 上叫什么？我搜不到。」

我去搜了。搜不到。

接着把另外三个目录也搜了一遍：npm 上 dsh-enterprise-ops 返回 404，Glama 返回 404，mcp.so 没有条目，Smithery 的搜索接口直接报错。四个主流 MCP 目录，一个都不存在。

这个项目有 98 个 MCP 工具、499 条路由、30 个插件。它作为一个 MCP Server，在 MCP 的地图上是不存在的。

更难受的是：这件事我们两个月前就知道了。punkpeye/awesome-mcp-servers（97.7k star）上那个 PR 从 10 月 17 日挂到现在，我还在评论区自己写了八条更新，最后一条是「Glama 是 blocker，且在我们这边」。

我知道问题在哪。我只是没改。

一、四个目录，同一份实测

先摆证据。全部是今天重新跑的，不是回忆：

目标结果判据
registry.npmjs.org/dsh-enterprise-ops404包从未发布，注册表里没有这个名
glama.ai/mcp/servers/@01men/ybkkasi404目录查不到服务条目
mcp.so/server/ybkkasi404无收录
Smithery 搜索 ybkkasi接口报错无收录

四个 404 背后是同一个根因，不是四次独立的失败。

二、根因是 package.json 第 4 行

打开仓库根目录的 package.json：

{
  "name": "dsh-enterprise-ops",
  "version": "1.6.0",
  "private": true,
  "bin": null
}

private: true。

这一个 boolean 做的事情比它看起来多：它让 npm publish 无条件失败，而 npm registry 是这条链路上的第一块多米诺。

  • npm 上没有包 → Glama 的自助验证拿不到包元数据 → 目录不给建条目
  • Glama 没有条目 → punkpeye/awesome-mcp-servers 的自动检查挂红 → 维护者不会合
  • 目录里没有 → mcp.so / Smithery 的同步器抓不到 → 也不会有

四个目录，一个 boolean，一条因果链。

private: true 不是失误。它是刻意的：这个仓有 packages/ 下 30 个包、内部有 docs/internal/ 一堆设计文档，误执行一次 npm publish 就能把半个仓库推上公网。用 private 锁死发布，是当时最省事的防呆。

省事的代价是：整个分发链路在第一步就死了，而症状出现在第 3、4 步。

三、为什么这个错会被读成「收录了但没流量」

这是这篇文章真正想讲的事。

当时我们内部的说法是「MCP 目录这条路没效果」。理由听起来很扎实：投了 14 个清单，0 个第三方 referrer。

但把判据换成「目标站能不能自助验证到这个包」，14 投的真实状态是：大部分根本没进入审核，少数进了但过不了自动检查。

这两件事在报表上是同一个数字——referrer = 0。

  • 「收录了，但没人从那里点进来」→ 渠道无效，砍掉
  • 「压根没收录，所以不可能有人从那里点进来」→ 执行缺失，与渠道无关

同一个 0，两种完全相反的含义。而人只会看见自己想看见的那个。

我们因此冻了 awesome 清单这条路径，写进了复盘：「14 投 0 referrer，该路径不可执行」。

后来 11 月 12 日 agentrust-io/awesome-ai-governance#164 被维护者合并了 —— 22 天前投的，一个 8 周里唯一存活的投递。它让结论变得很难看：不是清单无效，是我们投的方式有一半是废的，而另一条（这个仓不需要 npm 包，只看 README）恰好有效。

四、我们试过的三条绕路，全部失败

绕路一：加 glama.json 声明所有权。

10 月 23 日我在仓库根目录加了 glama.json，按 Glama 的 schema 声明 server 归属。结论：没用。Glama 的验证要求能拉到包或者能跑到容器，glama.json 只证明「这个 GitHub 仓库声称自己属于这个 listing」，证明不了「这个 listing 有东西可跑」。

绕路二：发 GitHub Release 当替代。

10 月 23 日打了 v1.3.0，后来又发 v1.5.0、v1.6.0。Release 是公开可下载的，看起来能替代 npm 包。

结论：对目录审核没用。四个目录的验证逻辑都指向包管理器或可运行的容器镜像，GitHub Release 不在它们的判据里。

绕路三：请维护者豁免。

我在 PR 评论区明确写过「不申请豁免」——因为那条规则是对的。一个要求「只有能跑起来的 server 才收录」的清单，如果为了某个项目开口子，它三个月内就会变成一张死链表。

三条绕路都失败的共同原因：它们都在绕开「包不可安装」这个事实，而不是解决它。

五、这件事的边界：目录收录不是分发渠道

写到这里要收一下，不然就成了「我们终于要发 npm 了」的预告——不是。

三个事实必须先讲清：

第一，这个项目的主安装形态是源码。 /api/platform/info 明确回 installMode: "source"。它要 Node ≥ 22.6、要 node:sqlite、要装配 30 个 cordis 插件，不是 npx xxx 一条命令能起的东西。发到 npm 上，用户下载完还是得 clone。包管理器解决的是「有没有」，不解决「能不能跑」。

第二，目录的流量从来不是主渠道。 8 周的数据：外部 referrer 只有 github.com。目录即使收录，能带来的也是长尾里的长尾。

第三，真正被这个 boolean 挡住的是「被验证」，不是「被使用」。 有人评估这套东西，会去翻 package.json（我们的 traffic top paths 里 blob/main/package.json 已经连续几天进榜），看到 private: true 之后会得出一个合理但错误的结论：「这大概是内部项目，不是给人用的」。

所以正确的动作不是「为了收录去发 npm」，而是：要么把可安装性做真，要么把「为什么不可安装」写在第一屏。

我们选后者。至少现在，package.json 里的 private: true 是诚实的——它就是不可从包管理器安装。

六、顺带修掉一个验证方法

查这四个 404 的时候发现一个更基础的问题，比上面的都值得说。

我们验证「页面是否上线」的方法，一直是 curl -o /dev/null -w "%{http_code}"。返回 200 就算成功。8 篇博客上线时都是这么验的。

今天顺手试了一下：https://ybkkasi.com/blog/nonsense-xyz/ 返回 200。

站点是单页应用，所有未命中的路径都回退到首页，永远 200。「200 = 页面存在」在这个站点上是完全失效的判据。

正确的验法是比对标题：

curl -s https://ybkkasi.com/blog/six-asset-model-cost/ | grep -o '<title>[^<]*</title>'
# <title>为什么我们把 6 类 AI 资产统一成了一套模型…… · 元冰可</title>

curl -s https://ybkkasi.com/blog/nonsense-xyz/ | grep -o '<title>[^<]*</title>'
# <title>元冰可 AIOS · 企业 AI 运行与治理平台</title>   ← 回退到首页

八篇博客这次全部重验过，标题各自独立、不是首页回退，确实在线。

但方法本身的漏洞是真的：任何一个「验证信号」在它失效之前，都会一直给你绿灯。 而失效的那一天，你不会收到通知。

我们前面那个 referrer = 0 是同一个病：一个读数为 0 的指标，看起来像「没人来」，实际是「管道断了」。两个都通过了我当时的验收，因为验收的方法本身不检查自己有没有在说谎。

七、如果你也在做 MCP Server

四条能直接查的，按顺序：

  1. grep '"private"' package.json。是 true 就检查一下：这个值是为了防误发布，还是因为没打算被安装？两者是不同的决定，混在一起就会像我们这样，两个月后才发现自己不在任何地图上。
  2. curl -o /dev/null -w "%{http_code}" https://registry.npmjs.org/<你的包名>。404 就是不在，没有第二种解释。
  3. 验证页面别只看 HTTP 码。SPA 站点会给每个不存在的路径返回 200，静态站会给每个不存在的路径返回 200（如果配了 fallback）。用页面里独有的字符串或者 <title> 做判据。
  4. referrer = 0 先分因。「来了没人点」和「压根进不去」在报表上同形。分不清就先去目标站搜自己的名字——搜得到再谈流量，搜不到谈执行。

八、现状

诚实地说，这一节是这篇文章唯一能给的承诺：

  • 四个目录仍然是 404，private: true 还在，本轮没有改
  • punkpeye/awesome-mcp-servers#16790 仍然 open，我不打算再催
  • agentrust-io/awesome-ai-governance 那条收录是真的，在 README 的 End-to-End Governance 段

下一步如果要动，只有两个选择：把 packages/ 拆出一个可发布的单包，或者彻底放弃「可安装的 MCP Server」这个定位，只做「可源码部署的自托管平台」。

两个都要改仓库结构，都不在本周的排期里。所以这一周，它继续是 404。
