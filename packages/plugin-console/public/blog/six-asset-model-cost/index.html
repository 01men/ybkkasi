为什么我们把 6 类 AI 资产统一成了一套模型——以及其中 3 类的成本其实是假的

你们公司现在有多少个 AI 相关的东西在跑？

我拿这个问题问过几个团队，答案基本是三个版本：IT 说「MCP 服务大概七八个吧」，业务说「Agent 有十几个，具体哪些还在用不知道」，财务说「模型开了四家的账号，账单每月四万多」。三份台账，零重合。

这不是管理懒，是这六类东西天然长得不一样：

  • MCP 服务有健康状态、有调用量、有版本，是「在线服务」的形状
  • Skill 是给人用的提示词包，没有「运行中」这个状态，只有「发布/待审」
  • Agent 是编排体，自己不产生 token，产生 token 的是它调用的模型
  • 模型 是平台自营的，没有「归属部门」，因为账单进来时就没带这个字段
  • AI 应用 是对外的壳，成本要看它背后调了什么
  • NAS 存储 连「调用」这个概念都不成立，只有容量和读次数

六种形状，六套字段，六张表。你问「谁在用 AI」，回答不了。

我们的选择是：不统一它们的实现，只统一它们的「可被问的那一面」。

一、统一的是什么，不统一的是什么

先看接口。/api/assets/inventory 返回的是一个扁平数组，六类混在同一个 items 里：

{"ok":true,"data":{
  "days":30,
  "total":27,
  "summary":{
    "byType":{"mcp":{"total":5,"inService":5},"nas":{"total":2,"inService":0},
              "agent":{"total":6,"inService":5},"app":{"total":3,"inService":3},
              "skill":{"total":7,"inService":6},"model":{"total":4,"inService":0}},
    "unhealthy":0,
    "costCents30d":34786
  },
  "items":[{"type":"mcp","id":"mcp_mvckdqnj53jiqei5","name":"数据分析引擎",
            "slug":"datawise","status":"online","health":"healthy","exec":"demo",
            "version":"1.8.0","org":"AI 平台部","updatedAt":"...",
            "calls":5,"costCents":9175}, ...]}}

items[] 里每一条都有这 11 个字段：

字段语义六类是否都有真实值
type六类之一全部
id / slug / name身份全部
status生命周期位置全部，但枚举值不通用（见下）
health健康只有 mcp / agent / app / model 有意义
org归属组织全部
updatedAt最后变更全部
calls30 天调用次数只有 3 类是真的
costCents30 天成本（分）只有 3 类是真的

统一的只有这 11 个「可以被跨类问」的字段。 版本号、endpoint、鉴权方式、依赖拓扑这些类内属性，一律留在各自的插件里，不进统一模型。

这是第一个关键决策：统一模型不是「大宽表」，是「共同投影」。把六类的所有字段熔进一张表，结果是一张 80 列、其中 60 列永久 NULL 的表，查询还得写 WHERE costCents IS NOT NULL 来绕开假数据。我们宁可只投影 11 列，然后把「这 11 列之外的事」交给各域自己的接口。

二、第一个代价：status 这个词在六类里不是一回事

统一 status 字段是最容易踩的坑。真实枚举：

类型status 取值
mcponline / gray / unhealthy / offline
skillpublished / pending_approval / draft / rejected
agentonline / trial / offline
modelonline / offline
apponline / offline
nasdraft / online

「在线」不是六类共有的概念。Skill 没有「在线」这个状态——一个提示词包不运行，它只是「发布了」。NAS 的 draft 意思是「还没挂上去」。

所以 inService 这个汇总指标只能靠枚举白名单算：

// packages/plugin-console/src/routes/dashboard.ts
const byType: Record<string, { total: number; inService: number }> = {}
for (const item of items) {
  const bucket = byType[item.type] ?? { total: 0, inService: 0 }
  bucket.total++
  if (['online', 'gray', 'published'].includes(item.status)) bucket.inService++
  byType[item.type] = bucket
}

['online','gray','published']——三个值来自三个不同的域，硬编码在这一行里。这是技术债，但它诚实：与其造一个抽象的 IN_SERVICE 状态机再映射回来，不如让这行代码显式承认「三类各有一个『在用』的说法」。

实测结果：skill 7 个里 1 个 pending_approval（合同条款审查），所以 inService=6；agent 6 个里 1 个 trial，inService=5；model 4 个全是 offline（待接入），inService=0。

如果这里做了抽象，这个 6/7 和 5/6 就永远对不上账了。

三、第二个代价，也是这篇文章真正想说的：3 类的成本是假的

看 costCents30d: 34786。这个数是真的——但它只来自一部分资产。

翻实现，每一类是怎么取 usage 的：

类型usage 取值方式真假
mcpusageOf('mcp:' + slug)真
modelusageOf('model:' + slug)真
appusageOf('app:' + slug)真
agentusageOf(undefined)恒为 0
skillcalls: skill.stats?.installs ?? 0，costCents: 0成本恒为 0
nascalls: 0，costCents: 0恒为 0

usageOf(undefined) 直接返回 {calls: 0, costCents: 0}。也就是说：

{"type":"agent","name":"数据分析师","calls":0,"costCents":0}

数据分析师 这个 Agent 它可能每天都在跑，但在这张台账里它永远显示「30 天调用 0 次、花费 0 元」。

这不是忘了写。真实原因是：成本账本的 key 是 resource 字符串，而 Agent 没有自己的 resource key。

模型调用发生的时候，计量写的是 model:deepseek-chat；它不知道这次调用是哪个 Agent 发起的。MCP 工具调用写的是 mcp:datawise；它也不知道是哪个 Agent 调的这个工具。Agent 是编排层，它的成本散在所有下游资源的账上，而账本里没有「这笔消耗归属到 agent:X」这一行。

这个问题不是「补个字段」能解的。要真解，得在每次模型/工具调用时把调用链上的 Agent 身份透传下来——这正是我们另一篇讲 MCP 通道漏传归属字段的越权复盘里同一个病根：编排层丢身份，下游就永远归不了因。

统一模型的第一个诚实成本：面板上看起来六类齐整，其中三类的数字是 0，而 0 不等于没有消耗，等于不归因。

我们选择把 0 显示出来，不做「估算填充」。因为按月账单 34,786 分推算，如果我把 Agent 成本按调用比例摊分回去，那个数会看起来漂亮得多，然后所有人都以为归因做完了。假数字比空数字危险。

四、那为什么还是要统一

既然三类归不了因，统一还有什么用？

用处在问句。统一之前，你问不出这些问题，因为答案散在六个接口里，字段名都不一样：

  • 「AI 平台部现在挂了几个在线的东西？」→ 按 org + inService 一行 SQL
  • 「有没有 unhealthy 的？」→ unhealthy: 0，一个数
  • 「最贵的三项是什么？」→ 按 costCents 降序（现回：数据分析引擎 9175、HR 人事服务 8859、客服工单系统 8440）
  • 「哪些资产 30 天一次没被调用过？」→ calls === 0

最后这条是我们内部最有用的一个查询，也是最容易被假 0 污染的一个。实测 27 个资产里 calls === 0 的有 20 条：

类型零调用这个 0 是真的吗
mcp1（汇率与结算，灰度中）真
skill2（合同条款审查、竞品舆情监控）真（installs=0）
model2（DeepSeek Coder / Reasoner，待接入）真
nas2（两个 draft）真
app0—
agent6（全部）假 0，usageOf(undefined) 硬编码

所以这个查询现在只能用来找「真闲置」，不能直接拿来当闲置清单——因为六个 Agent 混在里面，你没法只看结果就判断哪个是真没人用。我们内部的临时做法是先 WHERE type != 'agent' 再人工判断。

这正是上一节那个代价的下游后果：一个假的 0 会污染所有基于 0 的查询。 台账里填进一个不归因的默认值，代价不是那一格不好看，是依赖这一格的每一个问句都变成半真的。

统一模型真正的产品价值不是让报表好看，是让「没人用」这件事变得可查询——前提是每个 0 都是真 0。

五、六类之外的第七类

有个问题我们到现在没答案：「模型渠道」算不算一类资产？

byType 只有 6 个 key，但 platform/info 里的 resourceTypes 只注册了 3 类（nas / agent / app），mcp 和 skill 走的是另外的 registry，model 又是 modelgw 自己的表。六类在代码里其实是「2 + 3 + 1」三种装配方式，只是在投影层被拍平成 6 个 type 字符串。

早期版本对外说过「7 类」，把 SaaS 连接器也算了进去。后来对账发现 inventory 的 byType 里从来没有 connector——它有自己的生命周期，但不是「资产」，是「接入配置」。所以对外一律说 6 类，第 7 类是我们自己造出来的说法，已经删了。

顺带一个正在变的东西：collections 现在实测是 86（此前记录是 72）。这个数还在涨，说明存储装配还没稳定。所以对外文案里我们从不引用 collections 的数字——一个每天变的数写进宣传语，三个月后就是假话。

六、如果你也要建这本台账

三条能直接抄的：

  1. 只投影「可以跨类问」的字段，类内属性留在原处。 判断标准：这个问题，你会不会想拿它和别的类型比？会，才进统一模型。
  2. status 不要硬造统一枚举。 让汇总逻辑显式写白名单，比造一个抽象状态机再映射回来更不容易说谎。
  3. 归不了因的字段，显式返回 0 并在 UI 上标注。 不要摊分、不要估算、不要「暂无数据」这种含糊说法。0 就是「我们不归因这个」，让看的人知道边界在哪。

第三条最难，因为它要求你在一个看起来完整的面板上主动标出缺口。但台账的价值全在它敢不敢承认自己漏了什么——一份每一格都填满的台账，通常有三分之一的格子是拍的。
