30 插件 / 94 权限点 / 499 路由：把六类 AI 资产做成一本台账

先给结论，再给可复现的验证方式。

结论：企业 AI 资产治理的技术核心不是「加一层网关」，而是把每个能力域做成独立插件包，自己声明依赖、权限点和事件，跨域协作只走事件总线。这样资产台账、权限校验、成本归因、审计留痕才是插件自身的一部分，而不是外挂的补丁。

下面是真实可跑的命令，全部在本机实例 127.0.0.1:7302 实测通过（Node ≥ 22.6）：

# 1. 插件包数 / MCP 工具数 / 存储集合数
curl --noproxy '*' http://127.0.0.1:7302/api/platform/info

# 2. 路由矩阵：declaredApi / guarded / public / authenticated
curl --noproxy '*' http://127.0.0.1:7302/api/platform/route-matrix

# 3. 权限点目录
curl --noproxy '*' http://127.0.0.1:7302/api/iam/permissions

# 4. 资产台账：按类型汇总
curl --noproxy '*' http://127.0.0.1:7302/api/assets/inventory

第 2 条实测返回：

{"declaredApi": 499, "guarded": 458, "public": 30, "authenticated": 11, "undeclaredApi": 0}

declaredApi 是全部声明端点，guarded 是其中受权限点保护的子集——这两个数不能相减，也不能混着用（我们内部就踩过这个坑：老文档把子集当成全量写了个「受保护路由数」，是 v1.3 时代的字面量，已作废）。

一、架构：cordis 插件树，不是微服务也不是单体

整个平台实例就是一棵 cordis 插件树，和 dsh 用的是同一个插件框架。每个业务域一个独立包：

platform-core  iam  authn  usage  audit  audit-approval-reconcile
market  connector  mcp  nas  skillhub  agent  app  modelgw
connect  connect-host-api  update  update-api  portal  console
panel-core  flow-core  exec-hub  workforce  dingtalk-bridge  uhp  a2a
+ WorkforcePolicyRegistry  ToolRuntimeLite  resource-core

pluginCount 实测 30。这里有个口径坑值得说：packages/ 目录只有 29 个，但装配树里有 5 个非包级 fiber（WorkforcePolicyRegistry、ToolRuntimeLite、audit-approval-reconcile、connect-host-api、update-api），去重后净 +1。所以「包数」和「加载的插件数」本来就是两个数，硬统一成同一个数只会让其中一边变成假话。

关键约定有三条：

  1. 插件之间不直接读写彼此的数据。 跨插件协作只经事件总线和扩展点。边界靠接口契约，不靠约定俗成。
  2. 每个包自行声明依赖、权限点、事件，可以单独启停。治理能力是域自身的一部分。
  3. 平台自己也是一个 MCP Server，98 个 MCP 工具对外暴露，任何 MCP 客户端都能接。

配套是 25 个插件清单（plugin.yaml）和 9 份领域运维 Skill。

二、权限：fail-closed 的组织归属校验

权限点目录实测 94 个唯一 point，分基础 / 组织账号 / 资源 / 审批 / 计量 / 审计等组。

关键实现是组织归属校验默认 fail-closed：

// packages/plugin-iam/src/index.ts
// 组织归属校验 fail-closed（N1）。permissions 取操作者令牌实时解析结果（'*'=平台管理员）

要点是 permissions 从操作者令牌实时解析，不从请求参数收。客户端说「我是管理员」不作数。

内置角色是数据，不是代码：

角色权限面
super_admin*
org_adminconsole.login iam.* approval.read exec.* workforce.*
resource_adminmcp.* skill.* agent.* app.* nas.* 等
developer读多写少，iam.* 只读
member基础只读 + 面板
auditor全平台只读审计

注意 developer 是最小权限设计：提交和调试自己提交的资源，跨资源读是只读。

三、路由登记：两种注册形态都要扫

这是我们内部最容易被漏掉的一点。统计路由必须同时扫两种注册方式：

guarded('METHOD', '/path', 'perm')      → 一类
.register('METHOD', '/path', ...)        → 另一类

只扫 guarded( 会漏掉大量端点（OIDC 等走 .register）。我们早期就因为只扫一种，把数字报低了。

最终以 route-matrix 接口为准：499 条声明端点，其中 458 条受权限点保护、30 条免鉴权（自带凭证校验）、11 条仅 Bearer。

四、断言：1822 项，CI 里跑

自测断言 1822 项，CI quality-gate 在 Node 24 两个矩阵各跑一遍，实跑日志：

✔ 落地页断言数 1822 = 本次实际断言总数 1822（断言数防漂移）
自测结果：1822/1822 通过

最后那行「落地页断言数 = 本次实际断言总数」是防漂移自校验——如果前端落地页写了一个新数字而断言集没跟上，CI 直接红。我们被这个机制抓到过两次首页指标卡漂移（一次是插件数写旧，一次是断言数写成了两代前的值）。

五、跑起来

git clone https://github.com/01men/ybkkasi.git
cd ybkkasi
docker compose up -d     # 打开 http://localhost:7300

或者作为 dsh 插件接入（web profile）：

dsh plugin --profile web add github:01men/ybkkasi

从源码起独立实例（Node ≥ 22.6，node:sqlite，零重型运行时依赖）：

npm ci
npm start

在线只读演示：<https://demo.ybkkasi.com/>

几个我们没解决的：MCP 第三方服务常常不声明工具风险等级，早期我们默认「未声明 = 只读」，等于所有能写数据的工具只要保持沉默就绕过审批；改成「未声明 = 未知」后，写路径直接拒。另外场景级策略目前只支持「角色/用户 × 动作 × 允许/拒绝」，没有条件表达式、没有时间窗、没有数值约束。审批两级签核目前允许同一个人签两级（小团队凑不出两个人，我们选择去掉四眼原则，而不是逼大家共用一个 admin 账号）。
