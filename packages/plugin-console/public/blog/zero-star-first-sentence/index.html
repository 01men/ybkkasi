这不是「被埋没了」，是我把事情做错了一大半。

错误一：第一句话说的是「我做了什么」，不是「你有什么问题」

最早那版 README 开头大概是这么写的：

元冰可 · 企业 AI 资源管理平台
一套身份、一套权限、一套计量、一套审计。27 个插件，按需启用。

这句话的信息量，对一个刷 GitHub 的人来说是零。

他不知道「企业 AI 资源管理平台」对应他哪个具体的痛。他更不想关心你有多少个插件包——那是你实现层面的选择，不是他要解决的问题。他点进仓库的唯一理由是：这解决了我手上一个具体的麻烦。

后来的版本第一屏改成了这个：

你可能正在经历这些
· MCP 服务散在各处，没人说得清谁在用
· Agent 拿着一把万能 token 横冲直撞
· 模型账单月底出来，没人说得清哪个部门花的
· 出了数据问题，翻遍日志查不到审计记录

这四句话是我的产品真正存在的理由。 它们应该在第一行，不应该在文档第 15 节。

规则我现在定死：README 第一屏不允许出现任何产品名、任何技术名词、任何规模数字。只允许出现读者的症状。

错误二：把「我做得多」当成「我有价值」

4 万多行、几十个插件、三百多条路由——这些数字我看了三个月，越看越兴奋。

但对一个正在加班的人来说，499 条路由意味着什么？意味着读文档要花更久、部署出错概率更高、出问题更难定位。

规模大不是优点。我把「几十个插件，按需启用」放在第一屏，其实是在说「我做了很多」——这不是价值主张，这是工作量陈述。

真正该说的是：

  • 60 秒能跑起来（因为零运行时依赖）
  • dependencies 是空的，所以三年后你还能装得上
  • 出了问题只有 6 万行，不是 50 万行
  • MIT，所以你能改

规模是成本，不是卖点。可读性和可启动性才是。

这个认知的转变花了大概三周。我前五周一直在加东西，第六周才开始做减法——砍掉重复的能力、砍掉没人用的开关、把 60 秒启动从 4 分钟压下来。

错误三：我给自己造了一个不存在的「品类」

我原来的 README 里写过一句话，现在看是纯粹的自我感动：

这个品类国内外都没有成熟方案，我们要用内容把它定义下来。

这句话有两个问题。

第一，事实不对。 已经有至少三个玩家在做同一层的事：Monospace（从 Directus 出来做 governed）、Busabase（system of record）、AgentValet（IGA for AI agents，自托管还挂在 roadmap 上）。我是在自己没做竞品调研的前提下写的。

第二，动机不对。 我想做「品类定义者」，但我一个人维护这个项目。品类定义者需要持续输出，需要布道，需要被反复引用。我连一个稳定的使用者都没积累到。

写「没有竞争者」会招来专业读者开箱即用的反驳——那我在其他人开拆之前就输了一轮。

现在这句话改成：

这是一个刚被验证需求的新品类。网关上在做流量、可观测平台在做 trace、构建平台在做 Agent，但「企业里已经建成的那些 AI 资产归谁管」这一层还没有成熟答案。

从「我是第一个」变成「我在一条刚被验证的路上」。 后者是真的，而且抗打。

错误四：demo 要登录，等于没有 demo

我做了一整套免登录演示环境在最后才做出来。

在那之前，我的落地策略是「先注册后体验」。听起来很合理，但漏斗是这样的：

看到仓库 → 觉得有点用 → 去注册 → 填邮箱 → 建组织 → 等邮件 → 忘记密码 → 流失

每一步都在掉人。而这个项目的 demo 数据是我自己造的种子数据，本来就没什么隐私风险，我凭什么要求人先注册。

做完免登只读 demo 之后，首屏能直接点进去看，成本降为零。

顺带踩了一个坑，值得单说：我最初把演示环境做成了写隔离模式（写方法返回 405），后来觉得「让人点点看更真实」就放宽了权限。这是错的。演示环境的写操作一旦开放，它就不再是演示环境了，而是一个没有鉴权边界的数据入口。现在保持只读快照，写方法直接 405，我在 README 里专门写了一节说明这个取舍。

错误五：只在同类清单里等收录

前两个月我的分发动作基本是：给 awesome-mcp-servers 提 PR，等维护者合并。

这类 PR 的转化率很低。原因是结构性的—— awesome 清单的维护节奏是周级甚至月级，从提交到合并可能 3 个月，之后带来的流量也就那么一波。

现在我改了策略：

不做「我符合收录条件」，做「我值得被讨论」。

具体说，昨天我给 systempromptio/awesome-ai-agent-governance（主题完全重合，52 star）提了个 PR，body 里除了条目之外，还写清楚了这个项目不做什么（凭证轮转不如专用 agent-IAM、SaaS 多租户不是重点、单人维护）。写完自己就想：这条 PR 的价值不在于它会被合并，而在于如果维护者认真看了，他会记住这个项目。

分发不是把话喊出去，是让人在某个时刻想起你。

错误六：把「诚实」当成防守姿态

我把「诚实边界」写进 README 的时候，是当成免责声明写的：

本项目不转售不分账、不直连 NAS 私有 API、私钥存本地目录建议迁 KMS……

写完我松了口气，觉得这样就够诚实了。

但我后来意识到，诚实的价值在于说出来，而不是在于「我承认了缺点所以你不能怪我」。前者是给读者信息，后者是给自己免责。

同样一句话，两种写法：

免登演示态会向任何能访问端口的人开放实例的全部只读数据视图。默认关闭，仅限演示种子数据实例。

vs.

我们的演示环境没有鉴权面，所以别在生产用。

第一句给了读者完整的判断依据：他知道会发生什么、知道范围、知道默认状态。他自己会决定要不要用。第二句只是让他别用，然后什么也没学到。

诚实不是免责声明，是把决策权交回去。

所以现在到底怎么做

改了几件具体的事，都不是玄学：

改动之前之后
README 第一行产品名 + 规模数字读者的四个症状
落地页先注册免登录只读 demo
分发等 awesome 清单收录清单收录 + 社区技术补充回复
对竞品声称无竞争者明确「刚被验证的新品类」，并列出相邻玩家
诚实边界免责声明式给判断依据，不替读者下结论
数字越大越好只留能证明「省事」的那些：60 秒、0 依赖、MIT

边界

我做的事情里有几件是明确的失败：

  • 两个月 0 star、0 fork 是事实，206 次提交没有换来任何关注度
  • 品类定义者的目标超出了单人维护者的能力范围，我改了目标，不改承诺
  • 那些 awesome PR 大概率不会很快被合并，我把它们当成长期资产而不是即时渠道
  • 竞品已经有人在做，「没有成熟方案」这句话不成立

我也不敢说这次 PH 首发能有多少票。7 天前这个仓库有 1 个 PR 被卡在别人的收录标准上，昨天新加的 14 个 topic 也只是刚打上标签。这些都无法证明任何事。

能证明的只有一件事：如果你也遇到了那四个问题，60 秒能跑起来看看。

https://demo.ybkkasi.com

不解决问题也没关系。至少你知道这条路有人走过一遍。
